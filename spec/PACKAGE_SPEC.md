# Planning Package Specification

**Spec version:** 0.1 (draft)

A *planning package* is a folder of Markdown files, plus one YAML manifest, that
captures everything decided about a project before code is written. It is the
canonical source of truth that coding agents (Codex, Claude Code, GitHub Copilot,
Cursor) read while they build the project.

The package is produced in Steps 1 and 2 of the workflow (ideation in Claude or
ChatGPT, exported as Markdown) and consumed by the scaffolder in Step 3, which
copies it into a new repository and generates the per-agent instruction files.

---

## 1. Design principles

1. **One source of truth, thin adapters.** Rules for agents live once, in
   `AGENTS.md`. Tool-specific files (`CLAUDE.md`, Copilot and Cursor rules,
   Claude skills) are generated stubs that point back to it. Nothing is
   written twice by hand.
2. **Plain Markdown, chat-friendly.** Every artifact can be pasted into or
   exported from a chat window without tooling. Diagrams use Mermaid in fenced
   code blocks so they render on GitHub and stay diffable.
3. **Stable IDs and traceability.** Features, requirements, milestones, tasks
   and decisions carry IDs so agents and humans can reference them precisely
   (`F-03`, `FR-012`, `M2`, `T-2.4`, `ADR-0003`).
4. **Status is explicit.** Each artifact declares whether it is `draft`,
   `review` or `approved`. Agents treat `approved` content as binding and
   `draft` content as guidance.
5. **Small, ordered files.** Numbered filenames give a reading order and keep
   each file focused enough to fit comfortably in an agent's context.

## 2. Package layout

```text
<slug>-plan/
├── package.yaml                 # manifest (required)
├── AGENTS.md                    # canonical agent instructions (required)
├── planning/
│   ├── 00-idea.md               # raw idea + ideation notes (required)
│   ├── 01-vision.md             # problem, users, goals, non-goals (required)
│   ├── 02-features.md           # feature catalog F-xx (required)
│   ├── 03-requirements.md       # FR-xxx / NFR-xxx with acceptance criteria (required)
│   ├── 04-architecture.md       # system context, components, data, Mermaid (required)
│   ├── 05-design.md             # UX, visual design, API & data contracts (required)
│   ├── 06-project-plan.md       # milestones M#, sequencing, risks (required)
│   ├── 07-backlog.md            # THE list of work items T-#.#, with status (required)
│   ├── 08-glossary.md           # domain terms (optional)
│   ├── README.md                # planning index, generated by `its link`
│   ├── wireframes/              # one .md per screen, ASCII or Mermaid; images allowed
│   │   └── README.md
│   └── adr/                     # architecture decision records
│       └── ADR-0001-<title>.md
└── playbooks/                   # repeatable procedures for agents (optional)
    └── <name>.md                # becomes a Claude skill + is linked from AGENTS.md
```

When scaffolded, the package maps into the repository like this:

| Package path         | Repository path                      | Notes                              |
| -------------------- | ------------------------------------ | ---------------------------------- |
| `AGENTS.md`          | `AGENTS.md`                          | copied, project facts filled in    |
| `planning/**`        | `docs/planning/**`                   | copied verbatim                    |
| `playbooks/*.md`     | `docs/playbooks/*.md`                | copied verbatim                    |
| `playbooks/*.md`     | `.claude/skills/<name>/SKILL.md`     | generated wrapper                  |
| *(generated)*        | `CLAUDE.md`                          | imports `AGENTS.md`                |
| *(generated)*        | `.github/copilot-instructions.md`    | points to `AGENTS.md`              |
| *(generated)*        | `.cursor/rules/00-project.mdc`       | `alwaysApply: true`, points to it  |
| *(generated)*        | `HANDOFF.md`                         | first-session brief for any agent  |
| *(generated)*        | `docs/planning/README.md`            | planning index (`its link`)        |
| `package.yaml`       | `docs/planning/package.yaml`         | kept for re-generation             |

Codex reads `AGENTS.md` directly, so it needs no adapter.

## 3. The manifest: `package.yaml`

```yaml
spec_version: "0.1"
profile: full                      # optional: full (default) or lite; see section 15

project:
  name: "Recipe Box"               # human name
  slug: "recipe-box"               # repo / folder name: lowercase, digits, hyphens
  summary: "Save, tag and search family recipes."
  license: "MIT"                   # optional

stack:                             # what the scaffolder sets up
  language: "python"               # python has a skeleton; anything else gets the generic one, with a warning
  runtime: "3.12"
  framework: "fastapi"             # optional
  package_manager: "uv"            # optional
  test: "pytest"                   # optional
  lint: "ruff"                     # optional

agents:                            # which adapter files to generate
  - codex
  - claude
  - copilot
  - cursor

commands:                          # copied into AGENTS.md so agents can verify work
  setup: "uv sync"
  test: "uv run pytest"
  lint: "uv run ruff check ."
  run: "uv run fastapi dev app/main.py"
  acceptance: "uv run pytest tests/acceptance"  # optional; held-out tests that only `its land` runs (section 17)

artifacts:                         # status of each planning file
  planning/01-vision.md: approved
  planning/02-features.md: approved
  planning/03-requirements.md: review
  planning/04-architecture.md: draft
  planning/05-design.md: draft
  planning/06-project-plan.md: draft
  planning/07-backlog.md: draft

first_task: "T-1.1"                # optional; HANDOFF.md names it, otherwise it tells agents to run `its next`
integration_branch: "main"         # optional; where readiness is read from in parallel work (section 17)
test_paths: ["tests/**"]           # optional; globs for test files the done gate protects (section 17)
gate:                              # optional; the done gate's settings (section 17)
  acceptance_path: "tests/acceptance/"  # held-out tests: hidden from agents' worktrees, changes refused
  checks:                          # the mode of the checks that can be relaxed (section 17); `its scaffold`
    tests_pass_on_parent: enforce  # writes enforce for each warn-first check. enforce, warn or off
launch:                            # optional; the unattended commands `its start` prints (section 17)
  budget_usd: 5                    # --max-budget-usd for a headless Claude run (default 5)
its_source: "git+https://...@<ref>"  # optional; where scaffolded CI installs `its` from (default: this repo, pinned to the commit that scaffolded it)
```

Only `spec_version`, `project.name`, `project.slug`, `project.summary` and
`stack.language` are required. Unknown keys are preserved and ignored.

## 4. Artifact conventions

### 4.1 Front matter

Every file under `planning/` and `playbooks/` begins with YAML front matter:

```yaml
---
id: requirements          # stable, matches filename stem without number
title: Requirements
status: draft             # draft | review | approved
version: 0.1
updated: 2026-11-26
depends_on: [vision, features]
---
```

`status` in front matter wins over `package.yaml` if they disagree; the
validator reports the mismatch.

### 4.2 ID formats

| Thing            | Format      | Defined in             | Example   |
| ---------------- | ----------- | ---------------------- | --------- |
| Goal             | `G-n`       | `01-vision.md`         | `G-2`     |
| Feature          | `F-nn`      | `02-features.md`       | `F-04`    |
| Functional req.  | `FR-nnn`    | `03-requirements.md`   | `FR-017`  |
| Non-functional   | `NFR-nnn`   | `03-requirements.md`   | `NFR-003` |
| Component        | `C-name`    | `04-architecture.md`   | `C-api`   |
| Screen           | `S-name`    | `wireframes/*.md`      | `S-login` |
| Milestone        | `Mn`        | `06-project-plan.md`   | `M2`      |
| Backlog item     | `T-n.m`     | `07-backlog.md`        | `T-2.4`   |
| Decision         | `ADR-nnnn`  | `adr/`                 | `ADR-0003`|

IDs are never reused or renumbered (the one exception is a backlog
placeholder, `T-new-<name>`, which gets a permanent number when scheduled; see
section 11). Retired items are marked `~~F-07 Bulk import~~ (dropped, see
ADR-0004)` rather than deleted; a struck-through ID is still a definition.

### 4.3 Traceability rules

- Every feature links to at least one goal (`Supports: G-1`).
- Every `FR` names the feature it belongs to (`Feature: F-02`) and has
  testable acceptance criteria written as Given/When/Then or a checklist. In
  the lite profile features are headings in the requirements doc, so an `FR`
  names the goal it serves instead (`Supports: G-1`), and this rule is off.
- Every backlog item names the requirements it satisfies
  (`Satisfies: FR-004, FR-005`) and a definition of done (items with status
  `proposed` or `dropped` are exempt).
- Architecture components list the requirements they serve.
- Any choice that would be expensive to reverse gets an ADR.

### 4.4 Diagrams and wireframes

- Use fenced ` ```mermaid ` blocks for architecture, sequence, ER and state
  diagrams.
- Wireframes are one file per screen in `planning/wireframes/`, using an ASCII
  box sketch or a Mermaid block, followed by a list of elements, states
  (empty, loading, error) and the requirements the screen covers. Image files
  (`.png`, `.svg`) may sit alongside and be linked.

## 5. `AGENTS.md` contract

`AGENTS.md` is the only file every agent is guaranteed to read. It must stay
short (aim for under ~200 lines) and point to the planning docs rather than
repeat them. Required sections, in order:

1. **Project** — one paragraph: what it is, who it is for.
2. **Source of truth** — the planning docs, their reading order, and the rule
   that `approved` docs are binding; agents propose changes to them rather than
   silently diverging.
3. **Stack & commands** — setup, test, lint, run (from `package.yaml`).
4. **Repository layout** — where code, tests and docs live.
5. **How to work** — take the next `todo` item from `07-backlog.md`, keep its
   status current, reference IDs in commits and PRs, run tests before finishing,
   refresh cross-links after editing planning docs.
6. **Conventions** — code style, naming, error handling, testing expectations.
7. **Boundaries** — what agents must not do without asking (new dependencies,
   schema changes, changing approved docs, touching secrets).
8. **Playbooks** — list of `docs/playbooks/*.md` with one line each.

Commit convention used across agents:

```text
<type>(<scope>): <summary> [T-2.4]

Refs: FR-012, FR-013
```

## 6. Generated adapter files

These are generated by the scaffolder and should not be edited by hand. Each
begins with a marker comment so regeneration can detect manual edits.

```markdown
@AGENTS.md
```



## 7. Playbooks

A playbook is a repeatable procedure an agent can run, for example
`implement-task`, `update-plan`, `write-adr`. Front matter adds a
`description` field (one sentence, used as the Claude skill description). The
body is a numbered procedure with inputs, steps and a done-check. Playbooks are
plain Markdown so Codex, Copilot and Cursor can follow them via the link in
`AGENTS.md`, and Claude Code gets them as skills.

The template ships three default playbooks: `implement-task`, `update-plan`
and `write-adr`.

## 8. Validation

A package is **valid** when:

- `package.yaml` parses and has the required keys; `project.slug` matches
  `^[a-z0-9]+(-[a-z0-9]+)*$`.
- All required files exist and have front matter with `id`, `title`, `status`.
- Every ID referenced anywhere is defined exactly once.
- Every `F-` links to a `G-`; every `FR-` names an `F-`; every `T-` names at
  least one `FR-`/`NFR-` (unless `proposed` or `dropped`).
- Every backlog item has a valid `Status` and a `Milestone` that is defined
  (or `—`); every `Depends on` item exists, none is `dropped` while the item
  is open, and dependencies form no cycle. Placeholder IDs (`T-new-...`) appear
  only on `proposed` or `dropped` items, and `Touches` paths stay inside the
  repository. Every `Must` FR is satisfied by an item that isn't dropped.
- `06-project-plan.md` defines no tasks: no backlog-item headings and no
  checklists.
- Doc `status` is `draft`, `review` or `approved`; front matter is valid YAML;
  no file contains merge conflict markers; no ID is defined twice in one file.
- Every relative link resolves to a file, and every `#anchor` to a heading.
- Cross-links are current (`its link --check` would change nothing); this is a
  warning in `its validate` and a failure in `its link --check`.
- `AGENTS.md` contains the eight required section headings.

A package is **ready to scaffold** when it is valid and `01-vision`,
`02-features` and `03-requirements` are `approved` (in the lite profile, only
`03-requirements`). The scaffolder warns, but does not block, if other
artifacts are still `draft`.

## 9. Versioning

The spec uses `MAJOR.MINOR`. Minor versions only add optional fields or files.
The scaffolder refuses packages with a newer major version than it supports.

## 10. Chat export format

So a package can travel through a chat window, files are emitted inside marker
comments. Anything outside markers (conversation, questions) is ignored on import.

````text
<!-- file: planning/01-vision.md -->
```markdown
---
id: vision
...
```
<!-- end file -->
````

Rules for the importer:

- A block runs from `<!-- file: <path> -->` to the next `<!-- end file -->`.
- If the block's content is wrapped in a single outer code fence (three or more
  backticks, optional `markdown`/`md`/`yaml` tag), that fence is removed.
- If the same path appears more than once, the **last** occurrence wins, so a
  revised file later in the chat replaces the earlier draft.
- Paths must be relative, use `/`, and stay inside the package (no `..`).

## 11. The backlog

`planning/07-backlog.md` is the single, canonical list of work items. Nothing
else (the project plan, issues, code comments, agent scratch files) holds a task
list, so there is one place to look and one place to update.

```markdown
### T-2.1 — Store
- **Milestone:** M2
- **Status:** todo
- **Satisfies:** FR-001, NFR-002
- **Depends on:** T-1.1
- **Do:** what to build
- **Done when:** how a reviewer or test can tell
- **Verify:** `uv run pytest tests/test_store.py`
- **Touches:** `src/streak/store.py`, `tests/test_store.py`
```

| Field | Required | Value |
| ----- | -------- | ----- |
| Milestone | yes (`—` if unscheduled) | a milestone defined in `06-project-plan.md` |
| Status | yes | `proposed`, `todo`, `in-progress`, `blocked`, `done` or `dropped` |
| Satisfies | yes, unless `proposed` or `dropped` | `FR-`/`NFR-` IDs |
| Depends on | no (`—`) | other backlog items (`T-` IDs only) |
| Do / Done when | Done when expected for open items | prose |
| Verify | no | a command in backticks, a test ID, or `manual: ...`; how to check the item is done |
| Touches | no | comma-separated paths or globs relative to the repo root; used to keep parallel items apart |
| Kind | no | `test-only` for an item that only adds tests for behaviour that already exists: red on parent is skipped for it (section 17) |
| Verified | written by `its done` and `its verify` | the date the checks passed, the integration-branch commit the work was built on, and a hash of its Touches files (`2026-11-27, base 1a2b3c4d5e, tree 0a1b2c3d4e5f`) |
| Override | written by `its done` when a person waives the gate | the date, the waived finding kinds and the reason |
| Blocked / Dropped | written by `its block` and `its drop` | why |

Each field is one line (`- **Name:** value`). An empty field is empty; it never continues onto the next line.

- Items are in priority order. The next item is the first `todo` whose
  dependencies are `done`.
- The project plan defines milestones only; an item's milestone is its
  `Milestone` field, so membership is never stated twice.
- Agents may change the `Status` of the item they work on, in the same commit
  as the work, and may add items with `Status: proposed`. `its start` and
  `its done` make those changes (section 16); editing the field by hand is
  equivalent. A clarification that adds, removes or renames no ID and changes
  no scope may go in with the work (bump the doc's `version`, add a
  `Plan: <doc> — <change>` line to the commit). Any other planning change goes
  through the `update-plan` playbook.
- Item IDs follow `T-<milestone>.<n>` at creation; they are not renumbered if
  an item moves milestone.
- An agent proposing an item on a branch uses a placeholder ID,
  `T-new-<short-name>` (lowercase letters, digits and hyphens), instead of
  picking the next number, so parallel branches never collide. Placeholders are
  only valid on `proposed` (or `dropped`) items; a human assigns a permanent
  `T-n.m` when scheduling it.
- A proposed item may instead live in its own file,
  `planning/proposals/T-new-<name>.md`, holding just its section
  (`its propose` writes one). Two branches that each propose items then touch
  different files and never conflict. `its renumber` appends each proposal to
  the end of the backlog, deletes its file and gives it a permanent ID.
  Proposal files are not linked or validated as planning docs.
- A `blocked` item has a `Blocked:` field saying why, and a `dropped` one may
  have a `Dropped:` field; `its block` and `its drop` write them.
- Dependencies must not form a cycle, and an open item must not depend on a
  `dropped` one. Every `Must` requirement is satisfied by at least one item
  that isn't dropped.

## 12. Cross-linking and drift control

Agents navigate by following links, and every link is generated, so docs stay
traversable without hand-maintained cross-references. `its link` (run
automatically by `its import` and `its scaffold`) is idempotent and does three
things:

1. **ID links.** Outside headings, code blocks and inline code, every ID
   reference becomes a relative link to its definition: the ID's own heading if
   it has one, otherwise the section it is defined in, or its file (ADRs,
   wireframes). Existing ID links are re-pointed when a heading changes.
   Authors (and the chat prompts) write plain IDs; linking is the tool's job.
2. **Nav blocks.** Under each doc's title, a block between
   `<!-- its:nav ... -->` and `<!-- /its:nav -->` links the planning index,
   the docs in `depends_on` (upstream), the next doc in reading order, and every
   doc that references IDs defined here (**Referenced by**). The backlinks tell
   an editor exactly which docs to revisit after a change.
3. **Planning index.** `planning/README.md` is regenerated with the reading
   order and each doc's status, decisions, wireframes, and a table of where
   every ID is defined. It deliberately carries no backlog status or "next
   item": those change on every task branch, so a committed copy would go stale
   and conflict when parallel branches merge. `its next` and `its backlog`
   answer them live.

Drift is caught two ways: `its validate` reports broken links, undefined IDs
and stale cross-links; and `its link --check` exits non-zero when regeneration
would change anything (suitable for CI or a pre-commit hook); the scaffolded CI runs both. A backlog status
change never makes generated files stale.

## 13. ID recognition

IDs with an unmistakable shape (`FR-nnn`, `NFR-nnn`, `ADR-nnnn`, `T-n.m`) are
always treated as references, so a typo such as `FR-099` is reported. Shorter
shapes (`Mn`, `F-nn`, `G-n`, `C-name`, `S-name`) also occur in ordinary prose
("M1 Mac", "C-suite", "F-16", "S-expression"), so they count as references only
when the ID is defined somewhere, or when they appear in a traceability field
(`**Supports:**`, `**Feature:**`, `**Requirements:**`, `**Screens:**`,
`**Serves:**`, `**Satisfies:**`, `**Depends on:**`, `**Milestone:**`), where
nothing but IDs is expected.

A prose word that matches a *defined* ID ("we ship M1 first") is linked. Wrap it
in backticks to keep it as plain text.

An ID is defined by a heading that starts with it, a table row whose first cell
is the ID, or a line that starts with the ID in bold (`- **G-1** — ...`), in the
file that owns that kind of ID (section 4.2), plus ADR front-matter ids and
wireframe files named `S-<name>.md`.

## 14. Re-importing and re-scaffolding

- `its import` into an existing package leaves files that match the export
  alone (generated links and nav blocks are ignored when comparing). If any
  existing file differs, nothing is written and the conflicting files are
  listed; `--overwrite` replaces them and keeps each original as `<name>.orig`.
- `its scaffold` accepts a package folder or a scaffolded repo (it reads
  `docs/planning/package.yaml`). It refuses a target that overlaps its source.
  `--force` deletes an existing target only after confirmation (`--yes` skips the
  prompt; without a terminal, `--yes` is required).

## 15. Profiles

`profile` in `package.yaml` picks how much planning a project needs.

| | `full` (default) | `lite` |
| --- | --- | --- |
| Required docs | `00` to `07` | `00-idea`, `01-vision`, `03-requirements`, `07-backlog` |
| Features | `02-features.md`, F-nn IDs | `## Feature: <name>` headings in `03-requirements.md`; FRs cite goals with `Supports:` |
| Architecture, design, project plan | required | optional; add the file when it is worth writing |
| Milestones | every open item has one | optional (`—`) |
| Approved before scaffolding | vision, features, requirements | requirements |

`its new DIR --profile lite` creates a lite package. A lite package can grow
into a full one by adding the missing docs and changing `profile`.

## 16. JSON output

`its backlog`, `next`, `show`, `start`, `done`, `claims`, `release`,
`renumber`, `land`, `propose`, `promote`, `block`, `unblock`, `drop`,
`set-status`, `review`, `hooks`, `drift`, `verify`, `status`, `stats`, `gate-audit`, `link` and `validate` take `--json`. Output is one
JSON object on stdout, so agents never parse text or stderr, even when `its` hits a bug (`internal_error`) or the
command line is wrong (`usage`, exit 2). The global `-C DIR` runs any command as if from `DIR`: it is put in front
of the command's relative folder arguments.

Output on a pipe or a file is UTF-8 whatever the locale (cp1252 on most Windows machines). Files `its` writes are
UTF-8 with LF line endings on every platform. A backlog field edit, such as a status change, and `its link` keep
the file's own line endings.

- Every object has `"schema": 1` and `"ok"`. A new field is not a schema
  change; removing or renaming one is.
- A backlog item is `{id, title, status, milestone, satisfies, depends_on,
  done_when, verify, touches, placeholder, ready, blocked_by, file, line}`.
- `next`: `{source, item, ready (with --all), in_progress, claimed, waiting:
  [{id, title, blocked_by}], cycles}`, plus `parallel` and `held_back: [{id,
  overlaps, touches_listed}]` with `--parallel`. `item` is the first ready
  item that can start now, so `start` never refuses it for overlap; it is
  `null` when none can, and then `reason` says why: `overlap` (items are ready
  but may touch running work's files), `waiting` (on dependencies),
  `in_progress` (everything left is running, claimed or blocked) or `complete`.
  `source` is where statuses were read: `working tree`, or the integration
  branch's ref (section 17). `blocked: [{id, title, reason}]` lists `blocked`
  items. `stale_remote` is `{remote, fetched_at}` when there is a remote that
  wasn't fetched in the last hour (`fetched_at` is `null` if never), since
  claims made on other machines may then be missing; `null` otherwise, and
  always with `--fetch`. `status` has it too.
- `backlog` adds `proposals`: the items in `planning/proposals/`.
- `show`: `{id, kind, file, anchor, line, text, referenced_by}`, plus `item`
  for a backlog ID. `referenced_by` lists the docs that mention the ID: the
  ones to revisit when it changes.
- `start`: `{id, previous_status, status, forced, claim, item}`, plus
  `commands: {claude, codex, cwd, argv}` for a claim (`claude` and `codex` are
  shell lines quoted for the platform, cmd.exe on Windows, with steps joined by
  `&&`; `argv` runs without a shell, and
  `headless: {claude, codex, argv, cwd, result_file, settings, schema,
  budget_usd, env_unset, then}` gives the unattended commands of section 17), and
  `claim_held_here: true` when the claim is already this checkout's.
  `pushed` and `remote` say whether the claim branch was pushed, and
  `push_error` why a push failed for a reason other than losing the race. A claim is
  `{id, branch, remote_only, worktree, agent, started, finished, orphaned}`;
  `remote_only` means the branch exists only as a remote-tracking branch (another machine's claim), and
  `orphaned` means its ID isn't in the integration branch's backlog.
- `claims`: `{base, claims}`, where each claim adds `ahead` (commits not on
  the integration branch), `conflicts_with_base` (files a merge would
  conflict in, or `null` if this git can't tell) and `conflicts_with: [{id,
  files}]` for other claims. Each also says what its branch tip says, read from
  the backlog at the tip: `tip_status`, `blocked_reason`, `last_commit: {commit,
  date, subject}` (or `null`), `waiting_on` (dependencies not done on the
  integration branch) and `state`: `working`, `blocked`, `ready_to_land`,
  `conflicts`, `waiting`, `no_commits` (marked done with nothing to land),
  `finished` or `orphaned`.
- `status`: `{project, source, branch, base, counts, next, next_reason, ready,
  blocked, in_progress, proposals: [{id, title, file}], claims,
  ready_to_land, to_release, drift: {drifted, unknown}}`. `claims` are the
  active ones, with the fields above; `blocked` adds a `branch` for an item
  blocked on its claim branch; `in_progress` lists items in progress without
  a claim; `drift` is `null` outside git or when it can't be computed. `release`: `{id, released, deleted_branches,
  removed_worktree, deleted_remote_branches, remote_branches}`. `renumber`: `{dry_run, renumbered:
  [{from, to}], files, proposals_moved}`.
- `land`: `{base, dry_run, landed, skipped, released, pushed, proposals}`.
  Each entry is `{id, branch, landed, ...}`: a landed one has `commit` and
  `checks`; a skipped one has `reason` (`conflict` with `files`,
  `check_failed` with `checks`, `test_changes` or `outside_touches` with
  `findings`, `gate_error`, `base_moved`, `checkout_blocked`, `git_error`,
  `waiting` with `blocked_by`, `no_claim`, `no_commits`, `not_done` or
  `dry_run`) and `message`.
- `validate`: `{valid, ready, errors, warnings}`, plus `trace` with
  `--trace`: `{checked, criteria, requirements: [{id, title, file, criteria:
  [{ac, text, tests: [{file, line}], by_requirement}]}], uncovered: [{id, ac,
  text}], by_requirement}`.
- `drift`: `{drifted: [{id, title, satisfies, verified, verified_commit, files,
  commits, uncommitted}], requirements: [{id, items, files}], clean, unknown:
  [{id, reason, message}], no_touches, shallow}`. `verify`: the `done --check` object
  plus `verified` and `previous_verified`. `verify --drifted` and `verify --all`
  (every done item) return `{verified, failed}`: `verified` lists the objects for items that
  passed, `failed` is `[{id, code, message, ...}]`, and every item is tried.
- `review`: `{id, item, requirements: [{id, text, file}], base, merge_base,
  verify_source, touches_checked, findings, changed_files: [{status, path,
  old_path}], diff, diff_truncated, omitted, prompt, reply_schema,
  commands}`. `review --reply`: `{passed, verdict, min_severity, blocking,
  unmet, findings, requirements}`. `hooks`: `{command,
  written, unchanged}`.
- A gate finding is `{kind, message, ...}`, where `kind` is `verify_changed`,
  `test_deleted`, `assertions_removed` or `skip_added` (test changes), or
  `touches_changed` or `outside_touches` (scope changes, with `files`),
  `policy_changed`, `item_changed`, `other_item_changed` or
  `agent_config_changed` (changes to what the gate reads),
  `assertions_weakened`, `test_disabled`, `test_config_changed`,
  `acceptance_changed` or `tests_pass_on_parent` (phase 7), `test_removed`
  (phase 9, with `tests`), `no_test_report`, `failures_hidden`,
  `no_tests_ran` or `tests_skipped` (phase 9, from the test report, with
  `check`), or `no_changes` (the branch changes nothing outside the planning
  folder, so nothing shows the item was implemented; it is dropped when
  re-verifying a done item). A refusal's error carries the refusing findings
  in `findings` and the rest in `warnings`.
- `propose`: `{id, file, item}`. `promote`: `{id, status, renumbered_from}`,
  plus `committed` (the short commit) when the change was committed: by default
  for `promote` and `renumber`, and with `--commit` for `block`, `unblock`,
  `drop`, `set-status` and `verify`.
  `block`, `unblock`, `drop`, `set-status`: `{id, previous_status, status}`,
  plus `deleted_file` when a proposal was dropped.
- `done`: `{id, previous_status, status, checks: [{name, command, exit_code,
  passed, output, results?}], checks_skipped, manual_verify, verify_source, touches_checked,
  findings, warnings, red_on_parent, verified, now_ready, merge_needed}`; `verified` is the value
  written to the item's Verified field. `verify_source` is where the Verify
  command was read (the integration branch's ref, or `working tree`);
  `findings` are the done gate's findings that were allowed. With `--check`:
  `{id, status, checks, ..., checked_only: true}`, and nothing is written. Checks are the
  item's `Verify` command, then `commands.test` and `commands.lint`, run from
  the repo root; they run only in a scaffolded repo, and `--no-verify` skips
  them. `Verify` is run only when its whole value is one backticked command;
  anything else (`manual: ...`, a test ID, prose that mentions a command) is
  never run, and is returned as `manual_verify` for a person to check. A check
  that runs pytest has `results`, the summary of its JUnit report: `{report:
  true, tests, passed, failed, errors, skipped, failed_tests, skipped_tests:
  [{id, file, reason}], files}`, or `{report: false, reason}` when it wrote
  none.
- An error is `{"schema": 1, "ok": false, "error": {"code", "message", ...}}`.
  Codes: `not_found`, `placeholder`, `not_placeholder`, `bad_status`,
  `already_started`, `already_done`, `blocked` (with `blocked_by`), `claimed`
  (with `claim`), `overlap` (with `overlaps`, `touches_listed`,
  `overlapping_touches`), `which_item`, `check_failed` (with `checks`),
  `no_status`, `duplicate_id`, `bad_backlog`, `no_package`, `no_base`,
  `not_git`, `not_integration_branch`, `worktree_exists`, `locked`,
  `nothing_ready` (with `reason`), `fetch_failed`, `push_failed`, `dirty`,
  `diverged`, `exists`, `bad_name`, `bad_title`, `no_reason`, `usage`,
  `test_changes` and `outside_touches` (with `findings`), `bad_hooks_file`,
  `bad_agent`, `bad_review`, `incomplete` (`promote`: the item has no Done when or Touches; with
  `missing`), `nothing_to_review` (`review`: the branch only changes the backlog),
  `gate_error` (the gate couldn't compare the branch, so it
  refused), `override_reason` and `override_needs_person` (a waiver without a
  reason, or without a person), `git_error`, `internal_error`. `done` returns
  `override: {waived, reasons}` when a person waived findings.

Exit codes, the same with or without `--json`:

| Code | Meaning |
| ---- | ------- |
| 0 | ok |
| 1 | error |
| 2 | bad command-line usage |
| 3 | `next`, `start --next`, `land`: nothing is ready (with `--parallel`: nothing can start alongside the claims) |
| 4 | `start`: a dependency isn't done |
| 5 | `done`: a check or the done gate failed; the status is unchanged |
| 6 | `start`: the item may change the same files as one already running |
| 7 | `land`: a branch could not land (it conflicted, failed the done gate or its checks, isn't done, has no commits, or the base moved); branches only waiting on dependencies don't count |
| 8 | `drift --check`: a done item's files changed after it was verified |
| 9 | `next`, `start --next`: every item is done |
| 10 | `gate-audit`: a seeded cheat was missed, or only warned about (unless `--allow-warn`) |

`its backlog --write` saves the `its backlog --json` object as
`planning/backlog.json` (`docs/planning/backlog.json` in a repo), and `start`
and `done` keep it current once it exists. It is a generated mirror for tools
that prefer a file: never edited by hand, gitignored, and not copied by
`its scaffold`. The Markdown backlog stays the only source of truth.

## 17. Parallel work

Several agents can work the backlog at once, each in its own branch and
worktree. `its` creates the branches and prints the command to start Claude Code
or Codex in each; it never launches an agent itself.

- **The branch is the claim.** `its start <ID> --worktree [PATH]` creates the
  branch `its/<ID>-<slug>` from the integration branch in a new worktree
  (default `../<repo>-<ID>`); `--branch` creates it and checks it out here. An
  item is claimed while any local or remote branch `its/<ID>` or
  `its/<ID>-...` exists and the item isn't `done` or `dropped` on the
  integration branch. `its next` never offers a claimed item, and
  `its start` refuses one. `its start --next` picks and claims the next ready
  item in one locked step.
- **Claims are pushed.** When the package has a remote (`remote` in
  `package.yaml`, default `origin`), `its start` pushes the new claim branch
  with a lease that requires the branch not to exist yet, so when two machines
  claim the same item the first push wins and the other's local claim is
  undone (`claimed`). `--no-push`, or `push_claims: false` in `package.yaml`,
  keeps claims local. `next`, `start` and `claims` take `--fetch` to read the
  remote first; when the local integration branch is strictly behind its
  remote-tracking branch, readiness is read from the remote one.
- **A lock makes claiming atomic on one machine.** While it checks
  readiness, claims and overlap and creates the branch, `its start` holds an
  OS file lock on `claims.lock` in `$(git rev-parse --git-common-dir)/its/`,
  the directory every worktree shares. Every backlog status write holds the
  same lock, so concurrent `start` and `done` never lose a change. The OS frees
  the lock when its holder exits, even after a crash. `claims.json` there
  records each claim's worktree, agent and start time. Outside git the lock
  lives in the system temp folder.
- **`in-progress` isn't committed on claim branches.** The branch already says
  so. The item's `done` is committed with the work (`its done` with no ID uses
  the item of the claim branch that is checked out).
- **Done means merged.** On any branch other than the integration branch
  (`integration_branch` in `package.yaml`, default `main`; `--base` overrides
  it), `next` and `start` read statuses from the integration branch's copy of
  the backlog, so a dependency counts only once it is merged there.
- **Only items confirmed apart run in parallel.** Running items are active
  claims and `in-progress` items. `its start` (with or without a branch)
  refuses an item whose `Touches` might overlap a running item's, with exit 6,
  unless `--allow-overlap`. `its next --parallel [N]` offers up to N ready
  items (default 3) that overlap neither each other nor a running item. Two
  entries overlap when they could name the same file: equal paths, a directory
  and a path inside it, or a glob and anything under its fixed prefix. An item
  without `Touches` could touch anything, so it never runs alongside another
  item; it can start only when nothing else is running. A claim branch for an
  ID that isn't in the integration branch's backlog is reported as orphaned
  and blocks nothing. Only permanent IDs can be claimed.
- **Releasing.** `its claims` lists claims and marks finished ones;
  `its release <ID>` removes the claim's worktree and deletes its local branch.
  It checks everything first, so a refusal changes nothing: without `--force`
  the worktree must have no uncommitted changes, and the branch must be merged
  into the integration branch or the item done there. It refuses to remove the
  folder you are in. `--remote` also deletes its pushed branches on every
  remote: each is fetched first and deleted with a lease, so commits someone
  else pushed are never deleted unseen.
- **Renumbering.** Branches propose items with placeholder IDs
  (`T-new-<name>`). After merging, run `its renumber` on the integration branch:
  each placeholder that isn't dropped gets `T-<n>.<next free>`, where `n` is its
  milestone (`M3` gives `T-3.x`) or, without one, the milestone of the last
  numbered item above it. Every mention in the planning docs is rewritten and
  the docs are re-linked. `--dry-run` shows the new IDs first. It refuses to
  run off the integration branch (unless `--force`) or when a placeholder is
  proposed twice, and never reuses a number still mentioned in any doc.
- **The done gate.** An agent can edit the files its checks read, so before
  running any check `its done` compares the branch with what the item allows.
  The diff runs from the fork point to the working tree (uncommitted and
  untracked files included) and covers the whole repository, not only the
  package. On a claim branch the fork point is the merge base with the
  integration branch recorded when the claim was made. On the integration
  branch itself (a plain `its start`), it is the commit recorded at start,
  outside the working tree, so committed work is still checked.
  - The rules come from the integration branch: the item's Verify and
    Touches, and the `commands` and `test_paths` in `package.yaml`. A branch
    that edits `package.yaml` is refused (`policy_changed`).
  - The plan is diffed item by item. A branch may change its own item's
    Status, Verified, Blocked and Override fields and add proposals. Changing
    its Verify (`verify_changed`) or Touches (`touches_changed`), any other
    field of its item (`item_changed`), any other item (`other_item_changed`)
    or another planning doc is refused; another planning doc counts as
    outside Touches.
  - A deleted test file, a test that lost assertions (`assertions_removed`),
    a test that is gone (`test_removed`), or a new skip or xfail
    (`skip_added`) is refused. Assertions are counted test by test, and only
    those that can fail count: a test that keeps fewer than it had is a loss
    whatever the branch adds elsewhere, so commenting out an assertion and
    adding two `assert True` lines is still a loss. A test that is gone,
    deleted or renamed so the runner no longer collects it (`test_add` to
    `check_add`), is `test_removed` unless a test of that name turns up in
    another test file the branch changed; a test that asserted nothing that
    can fail may go. Python test files are read with `ast`, so a comment or
    `pass  # assert later` doesn't count as an assertion, and
    `pytestmark = pytest.mark.skip`, `@mark.skip`, `from unittest import
    skip; @skip`, `pytest.param(..., marks=pytest.mark.skip)` and an empty
    `@pytest.mark.parametrize("x", [])` count as skips. Other languages are
    read line by line with comments stripped, a test running from the line
    that starts it (`it("adds", ...)`, `test('x', ...)`) to the next; skips
    there include `it.skip`, `xit`, `t.skip()`, `test(name, {skip: ...})`,
    `{todo: ...}`, `.skipIf` and `.runIf`, and `.only`, `fit` and
    `fdescribe`, which stop the other tests running. Test files match
    `test_paths`, or by default `tests/`, `test/`, `__tests__/`, `test_*`,
    `*_test.*`, `*_spec.*`, `*.test.*` and `*.spec.*`.
  - Found, and in warn mode in projects scaffolded before phase 9 (below):
    an assertion that can't fail, such as `assert True`, `assert x or True`,
    `assert 1 == 1`, `assert 1 + 1 == 2`, `assert [x == 1]` or
    `assert (x, "message")` (`assertions_weakened`); a test that returns at
    once or only passes (`test_disabled`); a change to which tests are
    collected or run, or to their results: a `conftest.py` with
    `collect_ignore`, `pytest_collection_modifyitems`, a result hook
    (`pytest_runtest_makereport`, `pytest_sessionfinish`,
    `pytest_report_teststatus`, a hook wrapper, `exitstatus`, ...),
    `os._exit` or `pytest_plugins`; a test file that adds `os._exit`, an exit
    at import or `pytest_plugins`; changed pytest settings in
    `pyproject.toml`, `setup.cfg`, `tox.ini` or `pytest.ini`; a `pytest11`
    plugin entry point; a `sitecustomize.py`, `usercustomize.py` or `.pth`
    file; or a changed Jest, Vitest, Mocha or test-script setting
    (`test_config_changed`). New test files are checked against nothing, so a
    weak test the branch added itself is found too.
  - **The runner's report.** A check's exit code comes from the code under
    test, so it isn't trusted alone. When a check runs pytest (`pytest`,
    `py.test`, `python -m pytest`, `uv run pytest`, ...), it runs with
    `PYTEST_ADDOPTS` set to write a JUnit XML report to a fresh temporary
    folder (or the command's own `--junitxml` path wins), and the gate reads
    it after the checks pass. Every check runs without any `PYTEST_ADDOPTS`
    or `PYTEST_PLUGINS` from the caller's environment. A run that wrote no
    report stopped before pytest finished, for example on `os._exit(0)` in
    the code under test (`no_test_report`, warn first). A report with failed
    or errored tests behind exit 0 means something rewrote the exit status
    (`failures_hidden`). A report with no tests, or with every test skipped,
    shows nothing (`no_tests_ran`). Skipped tests that the item's Verify ran,
    or that are in test files the branch changed, are `tests_skipped` (warn
    first). `its done`, `its verify` and `its land` all apply these. This
    makes faking a pass harder, not impossible: code running inside the test
    process can still write a report of its own. A report with a `DOCTYPE`
    or entities, or one over 64 MB, counts as no report.
  - **Red on parent.** After the checks pass, the branch's new and changed
    test files are copied onto the fork point in a throwaway worktree, and
    Verify (or `commands.test` when Verify isn't a command) runs there after
    `commands.setup`. If it passes, the tests don't show the change does
    anything (`tests_pass_on_parent`, with `files` and `command`). `done`
    returns what ran as `red_on_parent: {ran, passed_on_parent, command,
    files, exit_code}`, or `{ran: false, reason}`. It is skipped when
    re-verifying a done item, and for an item with `Kind: test-only`, whose
    new tests are meant to pass on the code as it is.
  - **Held-out acceptance tests.** Tests under `gate.acceptance_path`
    (default `tests/acceptance/`) are left out of every worktree `its start
    --worktree` creates, by a sparse checkout (`start` returns `held_out`),
    and a branch that changes them is refused (`acceptance_changed`). `its
    land` runs `commands.acceptance` on each merged result after the other
    checks; `its done` never does. The folder is out of the agent's view,
    not secret: it is still in the repository's history.
  - **Warn mode.** The checks that can misfire on honest work
    (`assertions_weakened`, `test_disabled`, `test_config_changed`,
    `tests_pass_on_parent`, `no_test_report`, `tests_skipped`) start in warn
    mode: they are reported, with `mode: "warn"`, in `findings` and
    `warnings`, but don't refuse the item. `gate.checks.<kind>` in the
    integration branch's `package.yaml` sets `enforce`, `warn` or `off` for
    these and for `test_removed`, `failures_hidden` and `no_tests_ran`, which
    enforce by default. Every other check always enforces. When the
    package's `package.yaml` has no `gate` section, `its scaffold` writes one
    into the new repo that sets `enforce` for every warn-first check, so only
    projects scaffolded before phase 9 (or that set their own `gate`) warn
    first. Each finding has `mode`.
  - **Measuring the gate.** `its gate-audit [ID] [--no-run] [--allow-warn]`
    applies a fixed set of known cheats, one at a time, to a throwaway
    checkout of the integration branch and reports which the gate refused,
    which it only warned about and which it missed (`{ok, id, base,
    test_file, variants: [{name, description, expect, caught, found, mode,
    message}], caught, total, refused, warned, warned_kinds, missed,
    skipped}`). Most cheats need only the inspection. `os_exit` (`os._exit(0)`
    appended to the item's own Python source in Touches) needs the tests to
    run, so the audit runs `commands.setup` and the item's checks for it, and
    skips it when nothing shows the tests imported that source; `--no-run`
    leaves it out. `ok` is true only when every cheat was refused. It exits
    10 when any was missed or only warned about (`--allow-warn` accepts
    warnings), and prints the `gate.checks` settings that would refuse the
    warned ones. Nothing in the checkout changes.
  - Agent configuration (`AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, `.claude/`,
    `.codex/`, `.cursor/`, `.gemini/`, `.its/`, `.mcp.json`,
    `.github/workflows/`) is refused whatever the Touches say
    (`agent_config_changed`).
  - A changed file outside the item's Touches is refused, including a file
    outside the package in a monorepo (reported as `../path`). An item without
    Touches isn't scope-checked.

  Touches entries are paths relative to the package root: a plain path names
  that file or everything under that folder; a glob uses `*` (not crossing
  `/`), `**`, `?`, `[abc]` and `{a,b}`; every entry is also tried literally,
  so `app/[id]/page.tsx` works. The gate, `its land` and `its drift` share
  this one meaning.

  The gate fails closed: with no integration branch, a shallow clone, a fork
  point that left the history, or a git error, `its done` refuses with
  `gate_error` (exit 5) instead of passing.

  A person can waive a group: `--allow-test-changes=REASON` (test, plan and
  agent-config findings) or `--allow-outside-touches=REASON` (scope
  findings). A waiver needs a reason and a person: it is refused without an
  interactive terminal unless `ITS_ALLOW_OVERRIDES=1` is set by whoever runs
  the agent. On Windows the terminal has to be a console, since NUL, the stdin
  an agent's tool usually gets, also counts as a terminal there. The waived kinds and the reason are written to the item's
  `Override` field, and the waived findings are still reported. Verify is
  always the integration branch's, even when test changes are waived. A
  refusal never names the waiver flags; an agent that can't finish honestly
  runs `its block <ID> --reason`. `its land` runs the same gate on each
  branch before merging it.
- **Review and hooks.** `its review <ID>` prints an evidence bundle for a second
  agent: the item, the text of each requirement it satisfies, the gate's
  findings and the diff, with instructions to review once, only the diff, and
  answer with one JSON object (`its review --schema`): `{verdict: approve |
  changes_requested, requirements: [{id, status: met | not_met | cant_tell,
  evidence}], findings: [{severity: blocker | major | minor, file, line,
  message}]}`. The author's own account is left out, since it sways a
  reviewer: the backlog's diff and notes files (`HANDOFF.md`, `NOTES.md`,
  `PROGRESS.md`, `SUMMARY.md`, `WORKLOG.md`, `CHANGES.md`, `.its/`) are listed
  but not shown (`omitted`). `its review --reply FILE` reads the answer (bare,
  fenced, or inside a `claude -p --output-format json` envelope) and passes
  it when the verdict is approve, every requirement is met and no finding is
  at or above `--min-severity` (default `major`); otherwise it exits 5. A
  reply that doesn't fit the schema is `bad_review`. The item and requirement text come from the
  integration branch (a requirement the branch changed is flagged
  `changed_on_branch`), and the diff sits in a fence longer than any run of
  backticks inside it, so the change can't rewrite what it is judged against
  or close the fence. `its hooks` adds an opt-in Stop hook for Claude
  Code and Codex that runs `its hook stop`: it re-runs the gate for the
  item of the session's checkout (the `cwd` in the hook's JSON, so a session
  in a worktree is checked there) and, if it fails or the item isn't marked
  done, answers `{"decision": "block", "reason": ...}`. The reason carries the
  first failing check's output once, not once per check. It never blocks
  twice in a row, or when no item is being worked on or the item is blocked.
  A hooks file whose `hooks` or `hooks.Stop` has the wrong shape is refused
  (`bad_hooks_file`) and left as it was.
- **Landing.** A clean merge of two branches can still break the build, so
  `its land` merges finished claims into the integration branch one at a
  time, in backlog order, and runs the item's Verify plus the test and lint
  commands on each merged result. It runs from the main checkout on a clean
  integration branch, but merges and checks each branch in a throwaway
  worktree (running `commands.setup` there first, since a fresh worktree has
  no installed dependencies). Only a result that passes moves the integration
  branch, by a fast-forward of the user's checkout taken under the package
  lock; the checkout is never merged into, reset or cleaned, so untracked
  files and statuses written while the checks run survive. If the
  integration branch moved during the checks the item is skipped
  (`base_moved`); if an untracked file is in the way it is skipped
  (`checkout_blocked`) and the file is left alone. A claim is finished when its item is `done` at the
  branch tip, and lands only once its dependencies are done on the
  integration branch (an item whose dependency lands earlier in the same run
  gets its turn). Before merging, `git merge-tree` checks for conflicts; a
  conflict in a generated file (`planning/README.md`, wireframe index,
  `backlog.json`) is resolved by regenerating it, any other conflict skips the
  branch. A branch whose checks fail on the merged tree is never applied, so
  the integration branch only moves to states that were tested whole. `--fetch`
  fast-forwards from the remote first, `--push` pushes the result, `--release`
  releases each landed claim, `--dry-run` reports what would land. `its claims`
  shows each claim's conflicts with the base and with other claims ahead of
  time.

- **Unattended runs.** `its` never launches an agent; `its start` prints
  commands that do it safely (`commands.headless`):
  - `claude --bare -p PROMPT --settings FILE --output-format json
    --json-schema SCHEMA --max-budget-usd N --permission-mode acceptEdits
    --permission-prompts none`. `--bare` skips the project's hooks, so the
    settings file carries the Stop hook (`its hook stop`) and turns the OS
    sandbox on. It is written to `<git common dir>/its/launch/`, outside
    every worktree, so the agent can't edit it. The budget is
    `launch.budget_usd` (default 5).
  - `codex exec --sandbox workspace-write --output-schema FILE -o RESULT
    PROMPT`.
  - Push and registry tokens (`GH_TOKEN`, `GITHUB_TOKEN`, `NPM_TOKEN`, AWS
    keys, ...: `env_unset`) are unset for the agent, since `its land --push`
    does every push: by `env -u` in the line and in `argv`, or on Windows by
    `set NAME=` at the start of the line (in the console that runs it), and a
    program that runs `argv` there drops `env_unset` itself. Nothing printed
    skips permissions or the sandbox.
  - Each line ends with `its done ID --result FILE`. The result is one
    object, `{id, status: done | blocked | needs_human, summary, reason,
    files_changed, tests_run}` (`reason` is required unless `done`, other
    fields are refused), bare or as the `structured_output` of a `claude -p`
    envelope. `done` runs the gate and checks as usual; `blocked` or
    `needs_human` runs `its block` with the reason and commits it. A wrong
    `id` is `result_mismatch`, a file that doesn't fit is `bad_result`, and
    an envelope without `structured_output` (the run failed, ran out of
    budget or declined) is `no_result`; none of them change the item. `done`
    returns `result` and `run: {agent, cost_usd, turns, duration_ms,
    session_id}`.
- **The run ledger.** `start`, `done`, `block`, `land` and the Stop hook
  each append `{ts, item, event, outcome, ...}` to
  `<git common dir>/its/runs/<ID>.jsonl`: shared by every worktree on the
  machine, never committed and never in a diff, so recording can't trip the
  gate (an `.its/` folder in the checkout would be agent configuration) or
  conflict at land. `done` records its outcome (`passed`, `check_failed`,
  `test_changes`, `outside_touches`, `gate_error`, `no_result`), the finding
  kinds, the failed checks, the Touches count and what the agent reported.
  `its stats` reads it: `{items: [{id, attempts, passed, failed, blocked,
  landed, cost_usd, first_try, touches, agents}], records, attempted,
  first_try, first_try_rate, refusals, land, cost_usd, cost_p90_usd,
  by_size, by_agent, ledger}`. A `done --check` (and so the Stop hook) is
  recorded but isn't an attempt. Nothing in the ledger goes into an agent's
  prompt.
- **Sizing.** `its validate --sizing` adds `sizing: {checked, items,
  warnings: [{id, kind, message}], flagged}` for todo and proposed items:
  `too_many_touches` (more than 3), `too_many_requirements` (more than 2
  FRs), `too_many_criteria` (more than 5 Must acceptance criteria across its
  FRs), `no_verify` (no Verify command) and `vague` ("improve", "refactor",
  "clean up", ... in the title or Do, with no Done when). They are warnings:
  `validate` still passes. `promote` returns the item's as `sizing`.

## 18. Drift and traceability

A done item was checked against the code as it was then. Two commands say what
that guarantee still covers.

- **Drift.** `its done` and `its verify` write the item's `Verified` field,
  which ends with a hash of the files in its Touches as they were checked
  (`tree <hash>`). When the files on disk still match the hash, the item is
  clean, with no history needed; re-verifying changed code always writes a
  new value. When they don't, the history says which files changed: the commit that brought the current value into the branch (found on its
  first-parent history; for a landed item, the merge `its land` tested) is the
  item's verified commit. `its drift` lists each done item whose Touches differ
  between that commit and the working tree, with the commits that changed them,
  and the requirements those items satisfy. An item done before `Verified`
  existed uses the commit where it became done; one without Touches isn't
  tracked. `its verify <ID>` re-runs a done item's checks and refreshes its
  `Verified` value; commit it. In a shallow clone, an item whose `Verified`
  has no hash is reported as unknown (`shallow`), never as clean. `--check` exits 8 on drift.
- **Traceability.** Acceptance criteria are numbered by position in a
  requirement's **Acceptance criteria** list (`AC1`, `AC2`, ...); a bullet
  that starts with a label (`AC3:`) keeps that number, and an unlabelled
  bullet whose position a label already took gets the next free number. The
  label may be a heading, a bold line or a field-list bullet (`-
  **Acceptance criteria:**`). Only bullets at the first criterion's
  indentation count, so a sub-bullet is part of the criterion above it; the
  list ends at the next heading or bold label, even before its first bullet,
  so a later list such as **Out of scope** is never read as the criteria. A
  test covers a criterion when a test file names both, in any usual spelling
  (`test_fr_001_ac2_...`, `FR-001/AC2`, `FR-001, AC2`, `FR-001 (AC2)`, a
  marker such as `@pytest.mark.req("FR-001 AC2")`); a reference must end at
  a word boundary, so `fr0012ab` is not FR-0012. Naming the requirement alone covers all
  of its criteria, reported as `by_requirement`. `its validate --trace` lists
  the Must criteria no test names and exits 1 if there are any; plain
  `its validate` never fails on coverage. A requirement with no criteria list
  counts as one criterion.
